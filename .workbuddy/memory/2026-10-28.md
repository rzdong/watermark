## 项目启动：macOS 原生水印应用（Swift）

**需求要点**
- Swift 原生，禁止 Electron；安装包小、零外部依赖、纯离线
- 图片 + PDF 水印；自定义位置/平铺/角度/密度/内容；文字水印 + 图片水印
- 拖拽导入、处理状态、另存为；可打包 DMG 分发
- **硬约束（用户追加）：加水印不改图片质量与格式，不改 PDF 元信息与其它内容，零副作用**

**技术选型（已定）**
- 零第三方依赖，仅系统框架：SwiftUI + AppKit + ImageIO + CoreGraphics + CoreText + PDFKit(只读) + Compression
- 图片：CGImageSource 读 → 合成水印 → CGImageDestination 同格式/位深/色彩空间回写，元数据字典原样拷贝
  - PNG/TIFF/HEIC 可做到像素级保真；JPEG 只能"视觉无损"（解析原 DQT 反推 quality，无法数学无损）
  - 坑：EXIF 缩略图残留原图内容，需重建或剥离
- PDF：**增量更新（Incremental Update）**，不解压原内容流
  - 新 /Contents 数组 = [原内容流引用, 新水印流]；新 xref + trailer(/Prev)
  - 保留 /Info、XMP、书签、注释、表单、嵌入字体、图片零重编码、已有数字签名仍有效
  - 禁用 PDFDocument.write(to:) 与 CGPDFContext 重绘、禁止光栅化
  - 中文字体：CoreText 取 glyph path → PDF 路径填充指令（矢量、免字体嵌入）
  - 加密 PDF（trailer 含 /Encrypt）直接拒绝
- 铁律：原文件只读，一律输出新文件

**环境（实测）**
- macOS 15.7.4 arm64 / Xcode 16.4 (16F6) / Swift 6.1.2 / CLT 16.4 / Homebrew 已有 / hdiutil 已有

**踩过的坑（重要）**
1. 传统 xref 表：读完 subsection 的 count 后**必须 skipToNextLine**，否则首行被当空行吃掉，整表错位一行 → trailer 解析失败
2. 增量更新的 xref 表第一个 subsection 必须写 `0 1` 头，否则 reader 打不开
3. `NSData.compressed/decompressed` 会 throw；`COMPRESSION_RAW` 在 Swift 不可用
4. `CTFontGetPostScriptName` 不存在，是 `CTFontCopyPostScriptName`
5. `CGPath.applyWithBlock` 的 element 是 `UnsafePointer<CGPathElement>`，需 `.pointee`
6. **Apple ImageIO 的 JPEG 量化表是"低频平坦"型**（q=0.5 时低频全是 6），与标准 Annex K 表不成比例 → 必须按"与标准表之比是否恒定（CV<0.3）"分流，否则反推全错
7. SwiftPM 在本机必须加 `--disable-sandbox`，否则 sandbox-exec 被拒

- PDF 增量更新：原文件字节 prefix 完全一致、元数据(Title/Author/Subject/Keywords)不变、页数不变、可重新解析、/Contents 变两项数组且新流解压后含 cm/f/矢量轮廓
- 图片：PNG 进 PNG 出、尺寸位深不变、TIFF/EXIF 元数据保留、JPEG 档位反推（0.4/0.7 准确，>0.8 饱和误差 0.3）、动图被拒

## 第二轮：修复 9 个 bug（2026-10-29）

**PDF 水印写进去了却完全不显示——两个独立根因，都极隐蔽**

1. **版本号不能递增**。父节点 /Kids 引用的是「编号 + 原版本号」，Apple PDFKit 严格按版本号匹配。
   写新版本时若 gen+1，PDFKit 匹配失败就回退到旧页对象，表现为水印消失。
   → 增量更新写新版本时**沿用原 gen**；对象流中的对象 gen 恒为 0。
2. **PDFKit 拒绝自行生成的 zlib 流（/FlateDecode）**。
   NSData.compressed(using:.zlib) 与 compression_encode_buffer(COMPRESSION_ZLIB) 的产物都不被接受，
   只有不压缩才能显示。原文件内容流是压缩的且能显示，所以这个反差极具迷惑性。
   → 最终方案：**一律不自己压缩**
     - 文字 → Form XObject，字形路径全文档只存一份（体积从 30KB/页降到约 3KB）
     - 图片 → JPEG（/DCTDecode），由 ImageIO 产出标准 JPEG，PDF 原生支持
     - 内容流只放 `cm` + `Do`

**排查方法（值得复用）**：用「PDFKit 渲染第一页 → 比对像素」做验证，而不是只看结构断言。
结构全部正确（/Contents 数组、资源都在）但渲染无差异，正是这个 bug 的特征。
另：像素比对**必须比较 RGB 三通道**，只比 R 会把「白底 vs 纯红」判为无差异。

**其他修复**
- 文字翻转：`CGBitmapContext` 本身就是左下原点/y 轴向上，与 PDF 同构，**不要再 flip**，
  flip 反而让 CoreText 画出倒字（图片 CGImage.draw 不受影响，所以只有文字出问题）
- 字号滑块无效：tileWidth 只由 scalePercent 决定，缩放因子把字号影响抵消掉了
  → tileWidth = canvas × scalePercent × (fontSize / 28)
- 平铺重叠：步长要按**旋转后的外接框**（boundW/boundH）算，按 tile 自身宽高算纵向会叠
- UI：设置改为三个独立 NSPanel 悬浮面板；整窗接收拖拽；PDF 翻页预览；
  图片水印缩略图；清空按钮右边距；配置持久化到 UserDefaults（JSON 编码 WatermarkConfig）

## 第三轮：真实 PDF 加不上水印（2026-10-29，已用真实文件验证通过）

样本：`MINIAPP_PDF_02_多链接顺序_C4D7E9F2_wm_wm_wm.pdf`（ReportLab 生成，20KB，1 页）

**根因**：该文件已被旧版反复处理过三次，页对象 7 的 gen 已经是 1。
无论「沿用 gen」还是「递增 gen」都会失败：
- 沿用：同编号+版本的对象在文件里出现两次，PDFKit 挑先出现的（旧的）
- 递增：父节点 /Kids 引用不匹配（第二轮的根因）

**最终方案：不复用任何现有对象号 —— 重建整棵页树**
- 新页对象、新 Pages 节点、新 Catalog 全部用新编号
- 只在 trailer 里把 /Root 指向新 Catalog，彻底绕开版本号匹配
- 副作用更小：原对象连「覆盖」都没有，真正只追加
- 子树无变动的节点返回原引用，避免产生多余对象

**踩到的第二个坑**：Catalog 走的是 `/Pages` 不是 `/Kids`。
rebuild 只判 /Kids 的话，Catalog 会被当成叶子节点直接返回原引用 → 整棵树根本没重建，
/Root 仍指向旧对象，表现还是「水印写进去了但看不见」。必须先判 /Pages。

**回归测试**：`testRepeatedIncrementalUpdatesKeepWorking` —— 连续三轮「输出当输入」，
每轮都断言原字节保留 + 页数不变 + 渲染差异 > 0.01。

**给用户的建议**：已被旧版污染的文件（文件名带多个 _wm）里藏着若干不可见的旧水印流，
这些流的 /WMForm Do 会指向新的 Form，导致水印被叠加多层。
应当回到**原始文件**重新处理，不要在 _wm 文件上继续叠加。

## 第五轮：格式校验失效（2026-10-30）

**现象**：拖 .dmg / .zip 不拦截，全被当图片接受。

**根因（很隐蔽）**：`CGImageSourceCreateWithData` 对**任意二进制数据都返回非 nil**，
哪怕识别不出类型（`CGImageSourceGetType` = nil）、一帧都没有（`GetCount` = 0）。
原代码只判断「source 创建成功」，等于什么文件都放行。

**正确判定**（`WatermarkProcessor.kind(of:)`）：
1. 扩展名 pdf → PDF
2. `UTType(filenameExtension:)` 且 `conforms(to: .image)` → 图片（能挡住 dmg/zip）
3. 否则退回 ImageIO 嗅探，必须同时满足 `GetType != nil` **且** `GetCount > 0`

**文件位置**（以后改校验逻辑看这里）：
- 核心判定：`Sources/WatermarkCore/WatermarkProcessor.swift` → `kind(of:)`
- 拒绝收集 + 弹窗：`Sources/WatermarkApp/AppModel.swift` → `RejectedFile` / `add(urls:)` / `rejectionMessage`
- 按钮选择路径的限制：`ContentView.swift` → `chooseFiles()` 的 `allowedContentTypes`
- 测试：`Tests/WatermarkCoreTests/FormatDetectTests.swift`（含真实 DMG 回归）

## 第六轮：宽 PDF（发票）上水印显得重叠（2026-10-30）

**排查**：几何层面并没有重叠——`testNoOverlapAcrossCanvasShapes` 覆盖 A4 纵/横、
1400×500 宽发票、2000×300 极端宽、400×1200 窄长，逐对检测旋转外接框，全部不相交。

**真正原因**：水印尺寸基准取的是**画布宽度**。发票这类又宽又矮的页面会把水印撑得格外大
（1400×500 上 tileWidth 达 392pt），大水印挨在一起看上去就像叠了。

**改法**：基准改为宽高的**几何平均** `sqrt(w*h)`。
- 1400×500：392 → 234pt，块数 8 → 17，间距均匀不拥挤
- A4 纵/横现在得到一致的水印大小（原来横向页面水印明显更大）
- 副作用：已保存配置的观感会变（水印略小），用户需重新微调占比

**顺带**：平铺「间距」滑块下限从 0.5 改为 1.0 —— 小于 1 意味着步长小于水印自身外接框，必然重叠。

## 预览与导出不一致（2026-10-30）— PDFPage.draw 污染 textMatrix

**现象**：醉烧串发票预览里水印重叠、偏大，导出后正常；雄赳赳两份都正常。同一配置。

**排查**：tile 布局数据两边完全一致（12 块、同尺寸、最小中心间距 229.8），
CTM 与 mediaBox/cropBox 也一致，纯白画布上画不重叠 —— 所以不是布局问题。
用「墨迹差分」量化：预览墨迹 87154 px vs 导出 12068 px，比值 **7.22**（雄赳赳 1.05）。

**根因**：`PDFPage.draw(with:to:)` 渲染完 PDF 文本后，把 context 的 **textMatrix**
留在页面最后一次 `Tm` 指令的状态。实测：
- 雄赳赳 draw 后 textMatrix = identity（所以没问题）
- 醉烧串 draw 后 textMatrix = `a=d=3.175, tx=15.875, ty=-2.86`

`CTLineDraw` 依赖 textMatrix，于是预览里的水印被放大 3.175 倍且整体偏移。
PDF 导出走 CoreText glyph → 矢量路径，不经过 CGContext textMatrix，所以导出是对的。

**修复**：`ImagePipeline.drawWatermark` 在 saveGState 后显式 `context.textMatrix = .identity`。
修复后醉烧串墨迹比值从 7.22 降到 1.05，与雄赳赳一致。

**回归测试**：`TextMatrixTests` —— 对比 textMatrix 干净 vs 被污染两种情况下的水印渲染，
断言逐像素无差异；另断言污染状态下仍必须画出可见水印。
（教训：预览走 CTLineDraw、导出走矢量路径，两套绘制实现天然容易分叉，
凡涉及 CGContext 状态的都要显式重置。）

## 两个真实 PDF 打不开 + 兼容性与体积优化（2026-10-30 晚）

**现象**：招标文件（700K，91 页，含 Adobe.PPKLite 数字签名）与深蓝汽车合同（456K，iText 生成）
都报「PDF 结构异常：xref stream 解压失败」。

**根因（三个叠在一起，缺一不可）**：
1. `PDFCodec.inflate` 用 `(NSData).decompressed(using: .zlib)` —— 实测对标准 `78 9c` 流**一律返回 nil**。
2. 换成 `compression_decode_buffer(COMPRESSION_ZLIB)` 后仍错：它解的是**裸 deflate**，
   会把 zlib 的 2 字节头当数据吃掉。实测 333 字节输入应得 576 字节，却得到 328 字节垃圾。
   **正确做法：先校验并剥掉 zlib 头（CM=8 且 (CMF<<8|FLG)%31==0），再按裸 deflate 解。**
   用 Python zlib 独立验证拿到正确答案后反向定位出来的。
3. xref stream 的 PNG predictor：`/DecodeParms` 多数不写 `/Columns`，而规范规定行宽 = W 之和。
   按默认 1 字节行宽反解会整表错位（对象 type 出现 188/217 等非法值）。
   → `decodeStream` 增加 `defaultColumns` 参数，xref 侧传 rowLength；且必须**先解析 /W 再解压**。

**兼容性加固（本轮新增）**
- xref 链上单节点损坏只跳过不整体失败；xref 空或 /Root 丢失时**暴力扫描 `N G obj` 重建**
  （Catalog 必须解析验证 Type=Catalog 且含 Pages，只做字节匹配会认错）。
  实测：破坏 startxref 后招标仍解析出 91 页；深蓝救回 10 页（扫描无法区分增量历史页，兜底固有代价）。
- 页树 walk 同时认 /Kids 与 /Pages；坏节点跳过而非整份失败；加 visited 防环。
- 未知 Filter（Adobe.PPKLite 签名等）跳过而非判死；LZW 仍明确失败。
- 溢出/越界防护：/W 限 1...8、传统 xref 的 count 夹上限、/Length 夹到文件剩余、
  parseArray 在 skipWhitespace 后重新检查越界、扫描时 guard p > 0、tile 数上限 20000。

## 对象流丢页（2026-10-30 深夜）— 影响面最大的一个 bug

**现象**：深蓝汽车合同 10 页，只有第 4 页有水印，显示「完成 1 页」。招标文件 91 页却正常。

**排查**：Pages 节点 `/Count=10`、Kids 有 10 个对象（4,26,35,38,41,44,47,50,53,56），
但 `pages()` 只返回 1 个——其余 9 个在 `walk()` 里被 `continue` 静默跳过。
打印 xref 发现 10 个页对象**全在对象流 226 里**（type=2），只有对象 38 解析成功。

**根因**（`PDFRawDocument.objectFromObjectStream`）：
```swift
table[pair.number] = obj   // 按「对象号」建表
return table[index]        // 却用「在流中的序号」去取 ← 错位
```
xref 里 type=2 条目的 field3 是**序号**不是对象号。只有当序号恰好等于某个对象号时才命中，
且取到的是**错误对象**的内容。对象 38 的序号是 26，而 Kids 里恰好有对象 26 → 唯一"成功"的那个
其实是拿错了内容；其余序号在表里没有对应对象号 → nil → 被跳过。

**修复**：按序号建表 `table[order] = obj`，再 `table[index]` 取。

**为什么招标没事**：它的页对象走 type=1（文件偏移），不经过对象流。
**影响面**：现代 PDF（iText、Adobe、多数在线工具）广泛使用对象流，这个 bug 会造成大面积丢页。

**回归测试**：`PDFObjectStreamTests` —— 手工构造「页对象全在对象流 + xref stream」的样本
（Quartz 与 PDFKit 都不产出对象流，只能手搓）。已验证：把修复回退后这两个测试**都会失败**，
确认不是空转。

**排查教训**：丢页是静默的（walk 里 continue），没有任何报错。
建议以后凡遇「页数不对」优先打印 Kids 数量 vs pages() 数量 vs PDFKit pageCount 三方对比。

## 权限型加密 PDF：已自动支持（2026-11-02 上午）

**关键发现**：macOS 自带的 PDFKit **能直接解出无加密副本**，不需要 WPS 或任何第三方工具。
- `PDFDocument(data:).dataRepresentation()` 对 iText 的 AES-256（V=5 R=5）文档
  → 产出 **isEncrypted=false** 的副本，且能被我们的增量写入器正常加水印
- 前提是 `isLocked == false`（空密码可解锁），这正是「权限型加密」的定义

**实现**：`WatermarkProcessor.process(fileAt:)` 里检测到 `document.isEncrypted` 时，
先调 `WatermarkProcessor.unprotectedCopy(of:)` 解出副本，再对副本做增量加水印：
- detail 前缀标注「已解除保护」
- `isLossless = false`（整份重写，图片会被重编码）
- `unprotectedCopy` 内部**校验副本真的不加密**，否则返回 nil 让调用方报错

**实测（格网科技信用报告，11 页扫描件）**：
原 2.5MB → 输出 575KB，11 页全部加水印，输出不加密，
渲染确认文字清晰可读、水印可见、版式完整（画质可接受）。

**一个反直觉的坑**：PDFKit **解不开它自己写出的加密**
（`write(withOptions: [userPassword:])` 生成的样本，`dataRepresentation()` 和
`write(to:)` 都仍带加密）。所以回归测试无法用 PDFKit 造"可解密"的样本，
`EncryptedPDFTests` 里那条做了条件处理。真实第三方加密反而没问题。

**真密码保护的文档仍然拒绝**，文案改为「该 PDF 需要密码才能打开，请先解除密码保护」。

### 诊断方法沉淀（比结论更有用）
- 判断「平铺铺满没」：直接量 tile 外接框/跨度，别靠渲染图肉眼
- 判断「映射对不对」：放**单块**水印到已知视觉坐标，渲染测重心——
  这一步能给出干净的线性关系，比铺满后统计包围盒清晰得多
- 中心点无法区分两种 90° 旋转（中心对称），要用非中心的多个点

## 旋转页面：改用「摆正页面」——彻底解决（2026-11-02 傍晚，本轮最大成果）

**突破口来自用户**：他用预览.app「Cmd+P → 存储为 PDF」导出后再加水印就能铺满。
对比两个文件拿到了答案：

| | 原合同 | 预览.app 导出 |
|---|---|---|
| MediaBox | 0 0 842.04 595.44（横） | 0 0 595.28 841.89（竖） |
| /Rotate | 270 | **已删除** |
| 扫描图 | 2340×1654 | 2340×1654（**未重新编码**） |
| 体积 | 14.1MB | 14.2MB |

预览.app 做的是：**换 MediaBox 为视觉尺寸 + 删 /Rotate + 内容流外包旋转变换**，
图片只被引用、不重新编码 → **无损**。

**照做即可，且比打印导出更优**（保住文字层，不会光栅化）。

### 实现（PDFIncrementalWriter）
`makeUprightContent(for:)`（process 内的嵌套函数，需要 allocator/newObjects）：
1. 读原内容流（引/数组均可）→ `document.decodeStream` 解压拼接
2. 新流 = `q <matrix> cm\n` + 原内容 + `Q\n`（不压缩，内容流通常很小）
3. 摆正矩阵（原内容坐标 → 新页面坐标）：
   - 90°  `0 -1 1 0 0 W`
   - 180° `-1 0 0 -1 W H`
   - 270° `0 1 -1 0 H 0`   （W/H 是**原页面**的宽高）
4. 页对象：MediaBox 换成视觉尺寸、`removeValue(forKey:"Rotate")`
5. 之后水印按 `pageRotation: 0` 处理，不再写补偿矩阵

注：注释方案的 Form BBox / 注释 Rect 也要换成摆正后的尺寸（rectBox）。
`rotation == 0` 时 makeUprightContent 直接返回 nil，其他文件**完全不受影响**。

### 效果（销售合同）
- 输出 rotation=0、MediaBox (595.44, 842.04)
- 覆盖 **横向 99% / 纵向 86%**（之前 56%×42%），墨迹 41779（之前 13368，×3）
- 正文方向正常、不颠倒、无拉伸

### 回归
`PageUprightTests` 三条：旋转页摆正、摆正后铺满、无旋转页不动 MediaBox。
8 个真实文件全过（含原合同与预览导出两份）。60 测试全过。

**教训**：卡了两天的问题，是靠「用户给的正确样本 + 对比结构差异」解开的，
不是靠继续调参数。以后遇到坐标系难题，先想办法拿到一个「已知正确」的产物来对比。

## 体检与优化（2026-11-02 傍晚）

### 体积：不是问题，281K 那次是假象
- 可执行文件 692K（arm64 单架构），DMG 545K
- 已 Release 构建 + `strip -x -S` + ad-hoc 签名；`-Osize` 试过，无变化
- 链接的全是系统框架（AppKit/PDFKit/CoreGraphics/CoreText/ImageIO/SwiftUI…），**零第三方依赖**
- 曾出现过一次 281K，多半是构建异常复用了旧产物，不是真的变小

### 本轮改动
1. **清理死参数 `pageRotationDegrees`**：角度补偿取消后它已不起作用，
   却还在 WatermarkLayoutEngine / ImagePipeline / PDFPreviewRenderer 三层间传递。已移除，
   相应更新 PageRotationTests。
2. **批处理加 `autoreleasepool`**：整份 PDF 读入内存再产出一份，
   连续处理多个大文件时峰值内存成倍累积。
3. **预览刷新可取消**：拖滑块会连着触发渲染，旧任务不取消会排队渲染大文件，
   表现为预览滞后发涩。改为保存 Task、下次刷新前 cancel + `Task.isCancelled` 检查。
4. **更新过时注释**：`inverseRotationMatrix` 原先写「取自 getDrawingTransform 的逆」，
   该结论已被推翻（那个 API 不是渲染时真正用的变换），改为说明它只在回退路径生效。

## 应用图标（2026-11-02 晚）

**不用 AI 生成图**：产出物右下角带「AI生成 / WORKBUDD」平台水印，且纹理太碎，
缩到 16px 会糊成一片。改为**矢量绘制**。

实现：`Scripts/make-icon.swift`（纯 Swift + CoreGraphics，可直接 `swift Scripts/make-icon.swift`）
- 深靛 → 青渐变圆角底板 + 白色微倾文档 + 斜向半透明水印条 + 顶部水滴
  （「水」呼应中文语义，「斜向半透明条」直接表达水印功能）
- **按尺寸简化**：<64px 只画 2 条水印条且不画水滴，≥64 才画水滴，避免小尺寸糊成一团
- 输出 10 个规格的 iconset → `iconutil -c icns`

**踩坑**：`Resources/Info.plist` 原本**没有 `CFBundleIconFile`**，
光放 AppIcon.icns 不会生效。已补 `<key>CFBundleIconFile</key><string>AppIcon</string>`
（注意不带 .icns 后缀）。

**体积**：icns 597K（其中 1024px 一项就 297K），app 700K→1.3M，DMG 545K→1.1M。
试过 `-Osize`、`sips` 重编码，都压不动（渐变是主因，系统无 pngquant/oxipng）。
如需更小可去掉 `icon_512x512@2x.png`（1024），约回到 800K，代价是 5K 屏略糊。
